# Глава 2. Проектирование модуля сбора и обработки финансовых данных FinApp

## 2.1 Функциональные и нефункциональные требования

После анализа предметной области и существующих программных решений необходимо определить требования к разрабатываемому модулю. Требования позволяют формализовать ожидаемое поведение системы, определить границы разрабатываемого функционала и зафиксировать характеристики качества, которым должен соответствовать программный продукт.

В рамках настоящей выпускной квалификационной работы проектируется модуль сбора и обработки финансовых данных мобильного приложения FinApp. Данный модуль является первой функциональной частью системы и обеспечивает получение, нормализацию, категоризацию и первичное обогащение финансовых данных пользователя. Результаты работы модуля используются вторым модулем приложения — модулем анализа и контроля финансов — для построения дашбордов, бюджетов, целей, отчётов и уведомлений.

Основная цель проектируемого модуля заключается в создании подсистемы, которая позволяет пользователю быстро и удобно вносить финансовые операции в приложение, а системе — приводить полученные данные к единому формату и подготавливать их для последующего анализа. В проектных материалах по FinApp модуль сбора и обработки данных рассматривается как подсистема, обеспечивающая приём, нормализацию, категоризацию и обогащение транзакций из CSV/Excel, ручного и голосового ввода, а также выявление регулярных платежей и формирование первичных рекомендаций.

Система должна учитывать особенности предметной области. Финансовые данные могут поступать из разных источников, иметь разные форматы, содержать неполные сведения или ошибки. Поэтому проектируемый модуль должен не просто сохранять введённые пользователем операции, а выполнять цикл предварительной обработки: проверку корректности, нормализацию, определение категории, выделение контрагента или торговой точки при наличии таких данных, выявление повторяющихся платежей и подготовку результата для дальнейшего анализа.

С точки зрения пользователя модуль должен быть простым и понятным. Пользователь не должен выполнять сложную настройку перед началом работы. Основные сценарии должны сводиться к загрузке файла выписки, ручному добавлению операции или голосовому вводу транзакции. При этом пользователь должен иметь возможность просмотреть результат автоматической обработки и исправить его, если система определила данные некорректно.

### 2.1.1 Функциональные требования

Функциональные требования описывают действия, которые должна выполнять система. Для модуля сбора и обработки данных FinApp функциональные требования определяются основными сценариями работы пользователя и серверной части.

Первым функциональным требованием является поддержка импорта финансовых данных из файлов CSV и Excel. Пользователь должен иметь возможность выбрать файл банковской выписки на мобильном устройстве и загрузить его в приложение. После загрузки система должна определить структуру файла, извлечь строки с финансовыми операциями, сопоставить столбцы с внутренней моделью транзакции и сохранить обработанные данные.

Импорт файлов должен учитывать, что разные банки могут использовать различные форматы выписок. Например, в одном файле дата операции может называться «Дата», в другом — «Дата операции» или `operation_date`; сумма может быть представлена положительным или отрицательным числом; описание может содержать название торговой точки, служебный код операции или текстовое назначение платежа. Поэтому система должна поддерживать механизм сопоставления полей и приведения данных к единой структуре.

Вторым требованием является ручной ввод транзакций. Данный сценарий необходим для операций, которые отсутствуют в банковской выписке или должны быть зафиксированы пользователем самостоятельно. К таким операциям относятся наличные расходы, возвраты долгов, переводы между личными кошельками, корректировки импортированных данных и другие пользовательские записи. Форма ручного ввода должна позволять указать сумму, тип операции, дату, описание, категорию и при необходимости контрагента.

Для повышения удобства ручного ввода система должна предусматривать автоподсказки. При вводе описания или контрагента приложение может предлагать ранее использованные значения. При выборе похожей операции система может автоматически подставлять категорию, которая использовалась пользователем ранее. Это снижает количество ручных действий и ускоряет процесс ведения финансового учёта. В рамках проекта данное требование относится преимущественно к мобильному клиенту и может развиваться постепенно.

Третьим требованием является поддержка голосового ввода транзакций. Пользователь должен иметь возможность произнести операцию естественным языком, например: «Потратил 850 рублей на продукты» или «Запиши такси вчера на 430 рублей». Система должна принять аудиозапись, передать её на распознавание речи, получить текстовую расшифровку и извлечь из неё финансовые сущности: сумму, дату, категорию, описание и контрагента при наличии. После распознавания пользователь должен увидеть результат и подтвердить или исправить его.

Голосовой ввод является важной особенностью FinApp, поскольку он снижает трудоёмкость ведения учёта. Пользователь может выбрать один из поддерживаемых способов ввода — импорт CSV/Excel, ручной ввод или голосовой ввод, после чего мобильное приложение передаёт данные в сервис сбора, а серверная часть выполняет валидацию, нормализацию и дальнейшую обработку.

Четвёртым требованием является нормализация данных. Все транзакции, независимо от источника, должны быть приведены к единой внутренней структуре. Нормализация включает приведение даты к единому формату, преобразование суммы к числовому типу, определение признака дохода, расхода или перевода, очистку текстового описания, удаление лишних символов и стандартизацию источника операции.

Пятым требованием является валидация данных. Система должна проверять, что обязательные поля заполнены корректно. Например, сумма не должна быть пустой или равной нулю, дата не должна иметь неверный формат, тип операции должен принимать одно из допустимых значений, а пользователь должен иметь доступ только к собственным данным. При обнаружении ошибки система должна вернуть понятное сообщение, позволяющее пользователю исправить проблему.

Шестым требованием является выявление дубликатов. При импорте банковских выписок пользователь может загрузить один и тот же файл несколько раз или импортировать пересекающиеся периоды. Чтобы избежать искажения финансовой картины, система должна предусматривать механизм определения потенциально дублирующихся операций. Для этого могут использоваться дата, сумма, описание, источник, контрагент и хэш исходной строки файла. Данное требование фиксируется как проектное и может быть реализовано поэтапно.

Седьмым требованием является автоматическая категоризация транзакций. После нормализации операция должна быть передана в ML-сервис, который определяет наиболее вероятную категорию. Категоризация может учитывать описание операции, сумму, контрагента, источник и обученную модель. Если система уверена в результате, категория присваивается автоматически. Если уверенность недостаточна, пользователю может быть предложено выбрать один из нескольких вариантов. В текущей архитектуре ML-категоризация вынесена в отдельный Python/FastAPI сервис, а Go-сервис обработки может использовать собственные правила как резервный механизм.

Восьмым требованием является обогащение транзакций. Помимо категории, система должна добавлять к операции дополнительные признаки: нормализованное описание, контрагента или торговую точку при наличии, источник операции, вероятность регулярности, признак подписки и уровень уверенности модели. Эти данные необходимы для дальнейшего анализа и контроля финансов.

Девятым требованием является выявление регулярных платежей и подписок. Система должна анализировать историю транзакций пользователя и находить операции, которые повторяются с определённой периодичностью. К таким операциям могут относиться подписки на сервисы, оплата связи, онлайн-кинотеатры, облачные хранилища, образовательные платформы и другие регулярные списания. После выявления подписки система должна сохранить её в отдельной сущности и при необходимости сформировать первичную рекомендацию.

Важным ограничением является отсутствие прямого доступа к аккаунтам внешних сервисов. Поэтому индекс использования подписки в FinApp рассчитывается косвенно, на основе признаков транзакций, типа сервиса и эвристик, а не на основе фактической активности пользователя внутри стороннего сервиса.

Десятым требованием является сохранение истории импортов и обработки. Для каждого загруженного файла должна фиксироваться информация об импорте: имя файла, дата загрузки, количество строк, количество успешно обработанных операций, количество ошибок и статус обработки. Это позволит пользователю понимать, какие данные уже были загружены, а системе — обеспечивать повторную обработку при сбоях.

Одиннадцатым требованием является передача обработанных данных в общий контур FinApp. Модуль сбора и обработки данных не является изолированным. Его результатом должны быть структурированные транзакции, категории, подписки и рекомендации, которые в дальнейшем используются модулем анализа и контроля финансов.

### 2.1.2 Функциональные возможности пользователей

Основным пользователем модуля является физическое лицо, использующее приложение для управления личными финансами. В рамках проектируемого модуля не требуется разделение на сложные роли, так как система ориентирована на индивидуального пользователя. Однако можно выделить состояния пользователя: неавторизованный и авторизованный.

Неавторизованный пользователь имеет ограниченные возможности. Он может пройти регистрацию, авторизоваться в системе и получить доступ к основным функциям приложения. До авторизации пользователь не должен иметь доступ к операциям, импортам, подпискам и финансовым данным.

Авторизованный пользователь получает доступ к функциям модуля сбора и обработки данных. Он может загрузить банковскую выписку в формате CSV или Excel, добавить транзакцию вручную, воспользоваться голосовым вводом, просмотреть список операций, изменить категорию, исправить описание, подтвердить результат распознавания, удалить ошибочную операцию и просмотреть найденные подписки.

### 2.1.3 Функциональные возможности подсистем

Для реализации требований модуль делится на несколько логических подсистем: мобильный клиент, сервис сбора данных, сервис обработки данных, сервис анализа подписок, ML-сервис и база данных.

Мобильный клиент отвечает за взаимодействие с пользователем. Он отображает формы ввода, принимает файлы, записывает голосовые команды, показывает результат обработки и позволяет исправлять ошибки. Также клиент выполняет первичную проверку данных, например проверяет наличие обязательных полей и формат файла.

Сервис `collection` отвечает за приём данных. Он получает запросы от мобильного клиента, принимает файлы импорта, сохраняет информацию об импорте, создаёт транзакции и возвращает пользователю статус выполнения операции. Также данный сервис принимает аудиофайлы голосового ввода, передаёт их в ML-сервис для распознавания и сохраняет результат в таблицу голосовых расшифровок.

Сервис `processing` отвечает за пакетную обработку и обновление транзакций. Он может выполнять нормализацию, проверку статуса операции, присвоение категории и сохранение уровня уверенности. В архитектуре FinApp ML-категоризация выделена в отдельный ML-сервис, а `processing` может использовать rule-based подход как резервный или вспомогательный механизм.

Сервис `subscription-detector` отвечает за анализ регулярных платежей. Он обрабатывает историю транзакций пользователя, группирует похожие операции, выявляет повторяющиеся списания, определяет возможные подписки и формирует рекомендации по их оптимизации. Текущая реализация использует периодичность, сумму, описание, категорию и набор ключевых признаков.

ML-сервис выполняет задачи, связанные с машинным обучением и обработкой естественного языка. Он используется для распознавания голосового ввода, извлечения сущностей из текста и автоматической категоризации транзакций. Такой подход позволяет изолировать ML-логику от основных backend-сервисов и обновлять модели независимо.

База данных обеспечивает хранение пользователей, категорий, транзакций, импортов, подписок, рекомендаций и служебной информации. Также база данных используется для фиксации истории обработки, статусов операций и пользовательских исправлений.

### 2.1.4 Нефункциональные требования

Нефункциональные требования определяют качественные характеристики системы. Для модуля сбора и обработки финансовых данных особенно важны производительность, надёжность, безопасность, масштабируемость, удобство использования и сопровождаемость.

Требование производительности связано с тем, что система должна обрабатывать как одиночные транзакции, так и файлы, содержащие большое количество операций. Ручное добавление одной операции должно выполняться практически мгновенно с точки зрения пользователя. Импорт файла может занимать больше времени, но пользователь должен видеть статус обработки. Для batch-обработки целесообразно предусмотреть возможность обработки не менее 1000 транзакций в минуту, что соответствует проектным требованиям.

Требование времени отклика означает, что пользователь не должен ожидать длительное время при выполнении базовых действий. Добавление одной транзакции, открытие списка операций, изменение категории и подтверждение результата обработки должны выполняться с минимальной задержкой. Для операций, связанных с ML-обработкой, допустимо небольшое ожидание, однако оно должно сопровождаться индикатором выполнения.

Требование надёжности предполагает, что система должна корректно работать при некорректных входных данных, временных сбоях сети, ошибках распознавания речи и повторной загрузке файлов. При возникновении ошибки пользователь должен получить понятное сообщение, а система должна сохранить техническую информацию для диагностики.

Требование безопасности является одним из ключевых, поскольку приложение работает с персональными финансовыми данными. Доступ к данным должен предоставляться только авторизованному пользователю. Передача данных между мобильным клиентом и сервером должна выполняться по защищённому каналу. Все операции, связанные с изменением финансовых данных, должны быть связаны с конкретным пользователем.

Требование масштабируемости означает, что архитектура должна допускать увеличение количества пользователей, транзакций и импортируемых файлов без полной переработки системы. Для этого применяется микросервисный подход: отдельные сервисы отвечают за сбор данных, обработку и выявление подписок.

Требование удобства использования связано с тем, что пользовательское приложение должно быть понятным для человека без специальных знаний в области финансового учёта. Пользователь должен быстро понимать, как добавить операцию, загрузить файл, подтвердить голосовой ввод или исправить категорию.

Требование сопровождаемости означает, что программный код и архитектура должны позволять вносить изменения без нарушения работы всей системы. Например, ML-модель категоризации может быть обновлена отдельно от мобильного клиента, а сервис выявления подписок может развиваться независимо от сервиса импорта.

Таблица 2.4 — Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность | Обработка одиночных операций без заметной задержки; batch-обработка импортов |
| Время отклика | Быстрый ответ при ручном вводе, редактировании и просмотре операций |
| Надёжность | Обработка ошибок файлов, сети, распознавания и ML-категоризации |
| Безопасность | Авторизация, разграничение доступа, защищённая передача данных |
| Масштабируемость | Возможность увеличения нагрузки за счёт разделения сервисов |
| Удобство использования | Понятные формы, автоподсказки, подтверждение результата обработки |
| Сопровождаемость | Разделение логики по сервисам, независимое обновление компонентов |
| Совместимость | Поддержка мобильного клиента для iOS и Android |
| Восстановление | Возможность повторной обработки импорта при ошибке |
| Наблюдаемость | Логирование ошибок и ключевых событий обработки |

Таким образом, функциональные и нефункциональные требования определяют основу для дальнейшего проектирования модуля. Функциональные требования описывают, какие операции должна выполнять система, а нефункциональные — каким качественным характеристикам она должна соответствовать. На основании этих требований далее определяются входные и выходные данные, информационные потоки, архитектура микросервисов и структура базы данных.

## 2.2 Описание входных и выходных данных

Для проектирования информационной системы необходимо определить входные и выходные данные. Это позволяет установить, какие сведения поступают в систему, какие проверки выполняются, какие данные сохраняются и какой результат получает пользователь или другой модуль приложения.

В модуле сбора и обработки финансовых данных FinApp входные данные поступают из трёх основных источников: CSV/Excel-файлов, ручного ввода и голосового ввода. Дополнительно система получает данные авторизации пользователя, параметры обработки, пользовательские исправления и справочную информацию. Выходными данными являются структурированные транзакции, статусы обработки, результаты категоризации, найденные подписки, рекомендации и сообщения об ошибках.

### 2.2.1 Входные данные

Первую группу входных данных составляют данные регистрации и авторизации. Они необходимы для идентификации пользователя и разграничения доступа к финансовой информации. Пользователь должен иметь собственную учётную запись, так как транзакции, импорты, подписки и рекомендации являются персональными.

Для регистрации пользователя необходимы следующие данные:

- имя пользователя;
- адрес электронной почты;
- пароль;
- подтверждение пароля;
- согласие с условиями обработки данных.

Для авторизации используются:

- адрес электронной почты;
- пароль.

После успешной авторизации пользователь получает access token и refresh token, которые используются для доступа к API. На уровне проектирования важно учитывать, что все дальнейшие операции с финансовыми данными выполняются только от имени авторизованного пользователя.

Вторая группа входных данных — CSV/Excel-файлы банковских выписок. Такой файл содержит набор строк, каждая из которых соответствует финансовой операции. В зависимости от банка файл может иметь разную структуру, поэтому система должна уметь работать с несколькими вариантами формата.

Основные данные, которые могут содержаться в банковской выписке:

- дата операции;
- дата списания или зачисления;
- сумма операции;
- валюта;
- описание операции;
- контрагент или торговая точка;
- тип операции;
- номер счёта или карты;
- остаток после операции;
- служебный идентификатор операции.

Не все поля являются обязательными. Например, в некоторых выписках может отсутствовать контрагент или остаток после операции. В таком случае система должна обработать доступные данные и заполнить отсутствующие поля значениями по умолчанию или оставить их пустыми.

Третья группа входных данных — данные ручного ввода транзакции. Ручной ввод используется тогда, когда пользователь самостоятельно добавляет операцию в приложение. Для этого требуется минимальный набор обязательных полей.

Таблица 2.5 — Входные данные при ручном вводе транзакции

| Поле | Тип данных | Обязательность | Описание |
|---|---|---|---|
| Сумма | decimal | Да | Сумма операции |
| Тип операции | enum | Да | Доход, расход или перевод |
| Дата | date | Да | Дата совершения операции |
| Описание | string | Нет | Комментарий пользователя |
| Категория | uuid/string | Нет | Категория может быть указана пользователем или определена автоматически |
| Контрагент | string | Нет | Магазин, сервис или получатель платежа |
| Источник | enum | Да | Значение `manual` |
| Валюта | string | Нет | По умолчанию `RUB` |

Четвёртая группа входных данных — голосовой ввод. В этом сценарии пользователь передаёт в систему аудиозапись, содержащую описание операции на естественном языке. После распознавания аудио превращается в текст, а затем из текста извлекаются финансовые сущности.

Входными данными для голосового ввода являются:

- аудиофайл или аудиопоток;
- язык распознавания;
- идентификатор пользователя;
- дата создания записи;
- технические параметры файла;
- распознанный текст;
- результат извлечения сущностей.

Результат извлечения сущностей должен быть преобразован в структуру, аналогичную ручному вводу транзакции. Например, из фразы «Потратил 850 рублей на продукты вчера» система должна извлечь сумму 850, тип операции расход, категорию продукты, дату вчера в виде конкретной календарной даты и описание операции.

Таблица 2.6 — Входные данные при голосовом вводе

| Поле | Тип данных | Обязательность | Описание |
|---|---|---|---|
| Аудиозапись | binary | Да | Голосовая команда пользователя |
| Формат аудио | string | Да | Например, `wav`, `mp3`, `m4a` |
| Длительность | integer | Нет | Длительность записи в секундах, если доступна клиенту |
| Распознанный текст | string | После ASR | Текст после распознавания речи |
| Сумма | decimal | После NER | Извлечённая сумма операции |
| Дата | date | После NER | Извлечённая или вычисленная дата |
| Категория | string | После NER/ML | Предполагаемая категория |
| Контрагент | string | Нет | Извлечённый получатель или магазин |
| Уверенность | float | Да | Оценка уверенности распознавания или классификации |

Пятая группа входных данных — пользовательские исправления. Даже при использовании ML-категоризации система может ошибаться, поэтому пользователь должен иметь возможность исправлять результат. Исправления важны не только для текущей операции, но и для потенциального улучшения качества последующей обработки.

К пользовательским исправлениям относятся:

- изменение категории;
- изменение описания;
- изменение суммы;
- изменение даты;
- подтверждение или отклонение найденной подписки;
- удаление ошибочно импортированной транзакции.

Шестая группа входных данных — справочная информация. Она используется для корректной обработки транзакций. К ней относятся категории, пользовательские шаблоны, ранее использованные контрагенты, правила нормализации и параметры ML-модели. Часть этих данных хранится в базе данных и используется системой автоматически.

### 2.2.2 Выходные данные

Выходные данные модуля представляют собой результат обработки входной информации. Основным выходным объектом является структурированная транзакция. Она сохраняется в базе данных и используется как самим модулем сбора и обработки, так и модулем анализа и контроля финансов.

Структурированная транзакция должна содержать:

- идентификатор транзакции;
- идентификатор пользователя;
- сумму;
- тип операции;
- дату;
- описание;
- категорию;
- источник;
- контрагента или торговую точку при наличии;
- статус обработки;
- уровень уверенности ML-модели;
- признак регулярности;
- дату создания и изменения записи.

Это повышает прозрачность работы системы и позволяет пользователю контролировать качество импорта.

Результат импорта включает:

- идентификатор импорта;
- имя файла;
- дату загрузки;

- количество успешно обработанных транзакций;

Для каждой подписки система должна определить название или контрагента, сумму, периодичность, дату последнего списания и, при наличии достаточных данных, предполагаемую дату следующего списания.

Например, если система обнаружила подписку с низким индексом использования, она может предложить пользователю проверить необходимость её продления.

Шестым видом выходных данных являются сообщения об ошибках. Они необходимы для ситуаций, когда система не может обработать файл, распознать голосовую команду или сохранить транзакцию. Ошибки должны быть понятны пользователю и одновременно достаточно информативны для разработчика.

Примеры ошибок:

- неподдерживаемый формат файла;
- отсутствуют обязательные столбцы;
- некорректный формат даты;
- невозможно определить сумму операции;
- голосовая команда не распознана;
- не удалось определить категорию;
- операция уже существует;
- ошибка авторизации.

### 2.2.3 Связь входных и выходных данных

Входные и выходные данные модуля связаны последовательной обработкой. На вход поступает исходная информация: файл, ручная операция или голосовая команда. Затем система выполняет нормализацию, валидацию, категоризацию и обогащение. На выходе формируется структурированная транзакция, которая сохраняется в базе данных и становится доступной для дальнейшего анализа.

Общая схема преобразования данных может быть описана следующим образом:

```text
CSV/Excel-файл -> строки выписки -> нормализованные операции -> категоризированные транзакции -> сохранённые транзакции

Ручной ввод -> проверка данных -> ML-категоризация при необходимости -> сохранённая транзакция

Голосовая команда -> аудио -> текст -> извлечённые сущности -> транзакция -> подтверждение пользователя -> сохранённая транзакция
```

Такое разделение позволяет унифицировать обработку данных. Независимо от источника, результат должен быть представлен в едином формате транзакции. Это необходимо для согласованной работы всей системы FinApp.

Таким образом, описание входных и выходных данных показывает, какие сведения должен принимать модуль, какие преобразования он должен выполнять и какие результаты передавать пользователю и другим частям системы. Определение этих данных является основой для дальнейшего моделирования информационных потоков, проектирования базы данных и разработки API.
